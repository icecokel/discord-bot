# X 프로필 업데이트 감시 설계서

작성일: 2026-09-14 · 상태: 구현 완료, 운영 활성화 전 검증 필요

## 1. 목적과 기본 결정

Playwright로 Chromium을 실행해 <https://x.com/thsottiaux>의 게시물을 읽고, 새로 올라온 글을 기존 디스코드 봇의 관리자 DM으로 공유한다. 별도 서버나 데이터베이스 없이 현재 PM2 프로세스, node-cron, JSON 저장소를 사용한다.

사용자가 지정한 요구사항은 Chromium 수집, 대상 계정, 30분마다 배치 확인, KST 20:00~다음 날 07:00 알림 보류 및 07:00 일괄 알림이다. 수신처·업데이트 범위는 기존 봇 운영 방식에 맞춘 제안 기본값이다.

| 항목 | 기본안 |
| --- | --- |
| 감시 대상 | `thsottiaux` 한 계정의 게시물 탭 |
| 확인 주기 | 매일 24시간, 매시 00분·30분 배치 실행, `*/30 * * * *`, Asia/Seoul |
| 주간 알림 | KST 07:00 이상 20:00 미만에 확인한 신규 글 공유 |
| 야간 수집·알림 | KST 20:00 이상 다음 날 07:00 미만에도 수집은 계속하고 알림만 보류 |
| 아침 일괄 알림 | 07:00 배치에서 야간 보류 글을 모아 한 번에 공유. 없으면 발송하지 않음 |
| 수신처 | 기존 `ADMIN_ID` 관리자 DM |
| 업데이트 정의 | 최초 기준선 이후 생성된, 아직 알리지 않은 게시물 ID |
| 포함 | 본인 작성 게시물, 본인이 작성한 인용 게시물 |
| 제외 | 재게시 탭, 답글 탭, 다른 계정의 인용 원문을 별도 신규 글로 취급하는 동작 |
| 첫 실행 | 현재 글을 기준선으로 저장하고 과거 글은 발송하지 않음 |
| 공유 내용 | 작성자, 원문 발췌, 게시물 링크, 확인 시각 |
| 신규 없음 | DM 없이 실행 이력만 기록 |

이 버전의 ‘업데이트’는 새 글이다. 기존 글의 본문 수정·삭제, 프로필 소개 변경, 좋아요·조회수 변화는 감시하지 않는다. 한국어 번역·AI 중요도 분류·키워드 필터도 기본 범위에 넣지 않는다. 원문 공유에는 AI 호출이 필요하지 않다.

## 2. 확인한 사실과 미검증 사항

### 브라우저 확인

- 2026-09-14 KST에 Playwright 브라우저로 대상 URL에 접근했고 제목 `Tibo(@thsottiaux) / X`, 계정명, 게시물 본문과 개별 링크를 확인했다.
- 브라우저 UA는 `Chrome/152.0.0.0`으로 표시됐다. 운영 서버의 headless Chromium으로 재현한 결과는 아니다.
- 로그인 안내와 게시물 목록이 함께 표시됐다. 이 사실만으로 장기간 비로그인 수집이 가능하다고 보장하지 않는다.
- 상위 게시물 안에 다른 `article`이 중첩되는 인용 구조와 본문 ‘더 보기’ 버튼이 있었다.
- 검사한 상위 5개 게시물에는 `data-testid`와 `time` 요소가 없었다. `article[data-testid="tweet"]`, `time[datetime]`을 필수 조건으로 삼으면 현재 확인한 화면을 읽지 못한다.
- 일반 웹 조회 도구는 같은 주소에서 403을 반환했다. HTTP 조회 실패와 브라우저 수집 실패를 동일하게 취급하지 않는다.

본문 이해를 위한 예로, [관찰한 게시물](https://x.com/thsottiaux/status/2098685367058612394)은 리셋 적용 완료를 짧게 안내하면서 다른 글을 인용하고 있었다. 이런 구조에서는 외부 글과 인용 글의 ID·본문을 분리해야 한다. 게시물에 담긴 제품 관련 주장의 사실 여부를 검증한 것은 아니다.

## 3. 처리 흐름

```text
매시 00분·30분 / 관리자 수동 확인
  → 공통 실행 잠금 획득
  → 이력 읽기·검증
  → Chromium에서 프로필 수집
  → 작성자·게시물 ID·본문 분리 및 수집 상태 판정
  → 첫 실행이면 기준선 저장 후 종료
  → 신규 후보를 pending에 먼저 저장
  → KST 야간이면 pending을 유지하고 발송 없이 종료
  → 주간이면 pending을 오래된 글부터 발송 (07:00은 야간 모음)
  → 각 메시지 전송 성공 직후 포함된 글의 알림 이력 저장
  → 실행 결과 기록 / 브라우저 종료 / 잠금 해제
```

스케줄과 수동 실행은 동일한 서비스 함수를 사용한다. 잠금 범위는 수집부터 전송·저장까지이며 `finally`에서 해제한다. 단일 프로세스용 boolean 잠금이면 충분하다. 이미 실행 중이면 수동 요청에는 실행 중이라고 응답하고, 정기 실행은 기존 원장을 덮어쓰지 않고 건너뛴다. 다중 PM2 인스턴스는 지원 범위가 아니다.

### 알림 시간대와 07:00 모음

- 서버 로컬 시간대와 무관하게 `Asia/Seoul`로 판정한다. 보류 구간은 `[20:00, 다음 날 07:00)`이다. 정확히 20:00에는 보내지 않고 정확히 07:00부터 보낼 수 있다.
- 야간에도 30분마다 신규 글을 `pending`에 영속 저장한다. 작성 시각이 없을 수 있으므로 알림 보류는 게시물 작성 시각이 아닌 실제 발송 시각으로 결정한다.
- 07:00 배치에서 수집을 수행한 뒤 전날 야간에 쌓인 pending과 이번에 발견한 신규 글을 하나의 모음으로 보낸다. 별도 07:00 cron은 만들지 않는다. 실제 발송은 수집 완료 직후이며 수집 제한 시간만큼 늦어질 수 있다.
- 일괄 알림은 한 번의 배치에서 모아서 보내는 의미다. 한 메시지에 들어가면 하나로 보내고, 길이 상한을 넘으면 번호가 붙은 메시지로 나누어 같은 배치에서 순차 전송한다.
- 07:00 수집이 실패해도 이미 저장된 야간 pending은 보낸다. 수집 실패는 실행 결과에 남긴다.
- 07:00에 프로세스가 꺼져 있었거나 전송에 실패했다면 다음 주간 배치에서 남은 pending을 모아 재전송한다. 다음 날까지 무조건 기다리거나 이력을 지우지 않는다.
- 매 메시지 전송 직전에 시간을 다시 확인한다. 주간 배치가 20:00을 넘기면 나머지는 다음 날 아침까지 보류한다. 야간 수동 확인도 이 규칙을 따르며 실행 결과만 응답한다.

## 4. Chromium 수집

### 실행과 인증

- `playwright` 라이브러리의 `chromium.launch({ headless: true })`를 사용한다. 한 회차에 브라우저 하나를 열고 성공·실패 모두 종료한다.
- 초기에는 인증 없는 context로 검증한다. 로그인 화면만 나오거나 접근 제한이 발생하면 `auth-required` 또는 `blocked`로 종료한다.
- 인증이 필요한 경우 운영자가 직접 로그인해 만든 `storageState`를 읽도록 한다. 매 회차 비밀번호 입력 자동화를 만들지 않는다.
- 인증 파일은 프로젝트 내부 `.local/x-auth-state.json`에 보관하고 Git·배포 아티팩트·로그에서 제외한다. 소유자만 읽도록 권한을 제한한다.
- CAPTCHA나 계정 잠금은 우회하지 않는다. 해당 회차를 실패 처리하고 운영자가 세션을 복구한다.

Playwright는 브라우저 실행과 인증 상태 재사용을 제공한다. 쿠키 등이 포함된 인증 파일은 저장소에 커밋하지 않아야 한다. [라이브러리 문서](https://playwright.dev/docs/library), [인증 문서](https://playwright.dev/docs/auth)

### 추출 규칙

1. 프로필 제목·핸들과 게시물 영역을 확인한다. 광고·추천 영역은 대상에서 제외한다.
2. 중첩되지 않은 최상위 `article`을 수집한다. 인용 `article`은 별도 글로 승격하지 않는다.
3. 해당 article의 작성자 영역과 원문 링크를 짝지어 `thsottiaux` 본인 작성 여부를 확인한다. 모든 status 링크 중 첫 항목만 무조건 선택하지 않는다.
4. 게시물 URL은 `https://x.com/thsottiaux/status/<숫자 ID>`로 정규화한다. `/i/status/` 등 동일 글 링크는 중복 제거한다. ID는 문자열로 저장하고 비교할 때만 `BigInt`를 사용한다.
5. 본문 영역만 읽는다. 조회수·좋아요·버튼 텍스트·작성자 메타데이터·인용 원문을 통째로 합치지 않는다. 구체적인 본문 locator는 구현 시 정상 DOM 표본으로 확정한다.
6. 신규 후보의 본문이 접혀 있으면 검증한 상세 링크로 이동하거나 본문 확장 버튼을 사용한다. 확장에 실패하면 보이는 원문을 발췌로 표시하고 링크를 공유한다. 전체 본문이라고 표시하지 않는다.
7. 이미지 전용 글은 본문이 없어도 ID와 작성자가 유효하면 허용하고 ‘미디어 게시물’과 링크를 보낸다. OCR·영상 다운로드는 하지 않는다.
8. 정확한 작성 시간이 없으면 `publishedAt`을 비워 두고 확인 시각을 표시한다. 화면의 월·일만으로 연도를 추측하지 않는다.

상세 페이지 이동은 대상 계정의 검증된 게시물 링크로 제한한다. 글 속 외부 링크를 자동으로 방문하거나 본문의 지시를 실행하지 않는다.

### 수집 범위와 실패 판정

- 회차당 상위 게시물 최대 100개, 스크롤 최대 10회, 수집 전체 시간 최대 120초를 초기 상한으로 둔다. 이 값은 운영 검증 전 제안값이다.
- 스크롤할 때마다 ID를 누적한다. 가상 목록 때문에 마지막 DOM만 읽으면 앞에서 본 글이 사라질 수 있다.
- 기존 체크포인트에 도달하거나 목록 끝이 확인되면 정상 완료한다. 고정 게시물 하나 또는 기지 ID 하나를 만났다는 이유만으로 즉시 종료하지 않는다.
- 로딩 중·타임아웃·본문 구조 해석 실패·로그인 전환·차단을 빈 배열 성공으로 바꾸지 않는다. 이 계정에서 갑자기 글 0개가 반환되면 수집 이상으로 처리한다.
- 상한에 도달했는데 이전 체크포인트까지의 연속성을 확인하지 못하면 `partial / coverage-gap`으로 기록한다. 확인된 새 글은 보낼 수 있으나 완전 수집 체크포인트는 전진시키지 않는다.
- 최초 기준선은 정상 수집에서만 만든다. 최초에는 최근 100개 또는 정상적으로 진행한 10회 스크롤 범위를 기준선으로 사용하며 계정의 전체 과거 글 수집을 요구하지 않는다. 기준선 생성 도중 실패한 결과로 초기화를 완료하지 않는다.

이는 최근 목록 감시다. 장기 중단 중 생성됐다 삭제된 글, 목록에 노출되지 않은 글, 100개 범위를 넘는 공백까지 누락 없이 복원한다고 보장하지 않는다. 반복되는 공백은 운영자가 수집 상한을 조정하거나 재기준선 설정 여부를 판단한다.

## 5. 신규 판정과 상태 저장

`DATA_DIR/x-profile-history.json`을 사용한다. 현재 `DATA_DIR`는 개발 시 `src/data`, 운영 번들에서는 `dist/data`다.

| 필드 | 의미 |
| --- | --- |
| `version` | 상태 형식 버전, 초기값 1 |
| `account` | `thsottiaux`, 다른 계정 상태와 혼용 금지 |
| `initializedAt` | 최초 정상 기준선 저장 시각 |
| `baselineMaxId` | 초기 수집에서 확인한 가장 큰 게시물 ID, 이후 고정 |
| `lastCompleteMaxId` | 마지막 정상 수집의 최대 ID, 수집 범위 연결 확인용 |
| `notifiedIds` | 전송이 확정된 ID 목록 |
| `pending` | `{ id, url, text, textComplete, publishedAt?, observedAt }` 배열. 야간 보류와 전송 재시도에 공통 사용 |

최초 정상 수집에서는 초기 최대 ID를 저장하고 발송하지 않는다. 이후에는 `id > baselineMaxId`이면서 `notifiedIds`와 `pending`에 없는 글만 새 후보로 추가한다. 최초 기준선보다 오래된 글이 고정되거나 뒤늦게 나타나도 신규로 알리지 않는다. 단순히 매번 최대 ID보다 큰 글만 고르면 늦게 발견한 글을 놓칠 수 있으므로, 이후 판정은 고정 기준선과 ID 집합을 함께 사용한다.

단일 계정 초기 버전에서는 이력 ID를 임의 개수로 잘라내지 않는다. 삭제한 ID가 재등장해 중복 발송되는 문제를 피한다. 이력이 실제 파일 처리 병목을 만들면 그때 SQLite 등으로 이전한다.

### 전송·저장 순서

- 신규 후보를 디스크의 `pending`에 저장한 뒤 발송한다. 저장 실패 시 신규 알림을 시작하지 않는다.
- 주간에는 pending을 모아 길이 상한에 맞는 메시지로 순차 전송한다. 메시지별로 포함된 게시물 ID를 유지하고, 성공한 메시지의 글만 `notifiedIds`로 옮겨 `pending`에서 제거한 상태를 즉시 저장한다.
- Discord 오류가 나면 실패한 메시지의 글과 나머지 글은 다음 발송 가능한 배치에 재시도한다. 재수집 결과에서 글이 사라져도 저장된 pending은 유지된다.
- 수집 실패 시에도 주간에는 기존 pending을 전송할 수 있다. 야간에는 계속 보류한다. 이번 수집 실패는 별도로 기록하고 전체 결과를 성공으로 표시하지 않는다.
- JSON 손상·잘못된 스키마는 실패로 전파하고 자동 초기화하지 않는다. `writeJson`의 `false` 반환도 반드시 오류로 처리한다.
- 전송 성공 직후 상태 저장 전에 프로세스가 죽으면 같은 글이 다시 발송될 수 있다. Discord와 로컬 JSON을 하나의 트랜잭션으로 묶지 못하므로 정확히 한 번 전송을 보장하지 않는다. 누락보다 재시도를 우선하는 설계다.

## 6. 메시지와 운영 인터페이스

메시지 예시이며 실제 발송 결과가 아니다.

```text
🆕 X 새 게시물 · @thsottiaux

<원문 발췌>

원문: https://x.com/thsottiaux/status/<게시물 ID>
확인: 2026-09-14 10:00 KST
```

본문을 포함한 전체 content는 내부 상한 1,800자로 제한한다. 링크와 안내 문구 자리를 먼저 확보하고 원문을 자른 경우 ‘원문 일부’라고 표시한다. `allowedMentions: { parse: [] }`로 원문에 포함된 멘션이 작동하지 않게 한다.

07:00 모음은 `🌅 X 야간 업데이트 · @thsottiaux · N건` 제목 아래 글별 원문 발췌와 링크를 나열한다. 지연 재시도 시에는 ‘미전송 업데이트 모음’으로 표시한다. 분할이 필요하면 `(1/2)`처럼 순서를 붙이고, 게시물 하나가 두 메시지에 걸치지 않도록 발췌 길이를 줄인다.

- `/관리자 X확인`: 동일 수집·판정·전송 서비스를 즉시 실행한다. 처음이라면 기준선 생성만 한다. 야간이면 내용을 발송하지 않고 보류 건수와 07:00 발송 예정만 응답한다. 기존 관리자 DM 접근 제한을 따른다.
- `/관리자 스케줄상태`: 기존 화면에 X 항목을 추가해 기준선 생성, 신규 없음, 야간 보류 건수, 전송 건수, 로그인 필요, 범위 공백, 저장 실패 등을 표시한다. 야간 수집 성공·발송 보류는 정상 성공이며 오류가 아니다.
- 정기 확인 실패마다 별도 오류 DM을 추가하지 않는다. 실행 원장과 로그로 확인하며 신규 없음 DM도 보내지 않는다.
- 오류 로그에는 계정, 단계, 오류 코드, 건수, 경과 시간만 남긴다. 쿠키·토큰·전체 페이지 HTML은 남기지 않는다.

## 7. 변경 파일과 스케줄 호환성

| 파일 | 역할 |
| --- | --- |
| `src/features/x-monitor/x-profile-source.ts` 신규 | Chromium 생명주기, DOM 추출, 수집 상태 반환 |
| `src/features/x-monitor/x-monitor-service.ts` 신규 | 공통 잠금, 기준선, pending 처리, DM 메시지 생성·전송 |
| `src/utils/x-monitor-store.ts` 신규 | 상태 스키마 검증, 기존 JSON 유틸을 통한 저장 |
| `src/features/admin/commands/admin-x-monitor.ts` 신규 | 관리자 수동 확인 등록 |
| `src/core/scheduler/private-scheduler.ts` 수정 | 정기 실행 및 추적 연결 |
| `src/core/scheduler/schedule-definitions.ts` 수정 | `x-profile` ID·정의 등록 |
| `src/utils/schedule-run-store.ts` 수정 | 복수 분 단위의 다음 실행 계산 지원 |
| `package.json`, `package-lock.json` 수정 | `playwright` 런타임 의존성 고정 |
| `.gitignore`, `README.md` 수정 | 인증·실행 이력 제외, 실행 조건 및 운영 안내 |

파일명은 모두 kebab-case를 사용한다. 기존 `daily_news` 등 관련 없는 경로는 변경하지 않는다.

현재 `getNextScheduleRunAt`은 `hour` 또는 `hours`와 단일 `minute`으로 다음 실행 시각을 계산하므로 cron만 바꾸면 원장 시간이 어긋난다. `ScheduleDefinition`에 선택 필드 `minutes?: readonly number[]`를 추가하고, X 일정은 `hour: 0`, `hours: [0, …, 23]`, `minute: 0`, `minutes: [0, 30]`으로 정의한다. 다음 실행 계산은 정렬·중복 제거한 시·분 조합에서 현재 시각보다 뒤인 첫 시각을 선택하고, 없으면 다음 날 첫 조합을 선택한다. `minutes`가 없는 기존 일정은 `[minute]`을 사용해 동작을 유지한다. 주간·야간 구분은 cron이 아니라 공통 서비스의 발송 조건에서 처리한다.

`X_MONITOR_ENABLED=true`일 때만 정기 일정과 원장 조회 목록에 포함한다. 설정이 없으면 비활성으로 두어 배포 직후 브라우저 실행이나 알림이 시작되지 않게 한다. 수동 실행도 비활성 상태에서는 설정 필요를 응답한다. 인증 파일 경로는 프로젝트 내부의 고정 경로를 사용해 초기 설정 항목을 늘리지 않는다.

## 8. 구현·검증·도입 순서

1. **수집 검증**: 로컬 Chromium에서 대상 글의 ID·작성자·본문을 추출한다. 인용/긴 글/미디어/로그인 안내 표본을 확인하고, 발송 없이 서버 headless Chromium에서도 검증한다.
2. **상태 처리**: 기준선·ID 판정·pending 저장 및 오류 처리를 구현한다. 다음 표의 결정적 회귀 검사를 기존 Jest에 추가한다.
3. **봇 연결**: 서비스 하나를 정기 실행과 관리자 명령어에서 호출한다. 실행 상태는 기존 원장에 기록한다.
4. **운영 준비**: 런타임 의존성을 설치하고 프로젝트 내부 `.local/ms-playwright`에 Chromium을 설치한다. 설치와 PM2 실행에 같은 `PLAYWRIGHT_BROWSERS_PATH`를 지정한다. `.local/`은 Git에서 제외하고 배포 정리 대상에서도 보존한다.
5. **서버 검증 후 활성화**: 최초 실행은 기준선만 저장되는지 확인한다. 테스트 수신처의 전송 확인은 구현 단계에서 별도 승인된 범위로 진행하고, 운영 설정을 활성화한다.

Chromium 버전과 필요한 시스템 의존성은 선택한 Playwright 버전 및 서버 OS에 맞춰 설치한다. 기존 배포 워크플로의 파일 동기화·삭제 옵션도 확인해 인증 파일과 `dist/data`를 보존한다. [브라우저 설치 문서](https://playwright.dev/docs/browsers)

현재 PM2의 `300M` 설정만으로 Chromium 자식 프로세스까지 포함한 호스트 메모리 사용량이 통제된다고 가정하지 않는다. 수집 중 전체 메모리와 종료 후 브라우저 프로세스 잔존 여부를 측정한다. 검증 전 제한값을 임의로 높이거나 별도 worker를 추가하지 않는다.

### 인수 조건

| 검사 | 기대 결과 |
| --- | --- |
| 첫 정상 수집 A/B → 재실행 A/B | 기준선 생성, 발송 0건 |
| 주간에 기준선 A/B → 새로운 C → 다시 C | C 한 번 전송 |
| 과거 고정 글 재등장·조회수 변경 | 발송 0건 |
| 본인 글 내부에 타인 인용 article 존재 | 외부 글만 신규 후보, 인용 ID 혼입 없음 |
| 접힌 긴 글·미디어 전용 글 | 원문 일부 표시 또는 미디어 안내와 유효 링크 |
| 로그인 전환·빈 화면·타임아웃 | 신규 없음 성공으로 기록하지 않음, 기준선 유지 |
| 상한 도달·이전 범위 연결 실패 | partial, 완전 수집 체크포인트 유지 |
| 신규 글 전송 실패 후 목록에서 사라짐 | pending으로 다음 회차 재시도 |
| 모음의 두 번째 메시지 전송 실패 | 첫 메시지에 포함된 글만 확정, 나머지는 pending 유지 |
| 손상 JSON·pending 저장 실패 | 자동 초기화·신규 발송 없음 |
| 스케줄과 수동 확인 동시 호출 | 하나만 수집·전송 실행 |
| 00분·30분 정각 및 23:30 이후 | 다음 실행 날짜·시각이 cron과 일치, 기존 일정 계산도 유지 |
| KST 19:59:59 / 20:00:00 / 06:59:59 / 07:00:00 | 각각 발송 가능 / 보류 / 보류 / 발송 가능 |
| 야간 여러 배치에서 신규 글 수집 | 발송 0건, 중복 없는 pending 영속 저장 |
| 07:00 정상 배치 | 야간 pending과 이번 신규 글을 모음으로 전송, 완료 후 재발송 없음 |
| 07:00 pending도 신규 글도 없음 | 빈 모음 알림 발송 없음 |
| 07:00 수집 실패 | 저장된 pending 발송, 수집 실패 기록 유지 |
| 야간 재시작 또는 07:00 중단 후 07:30 복구 | 보류 이력 보존, 다음 주간 배치에서 미전송분만 모음 발송 |
| 야간 수동 확인·전송 중 20:00 경계 통과 | 야간 본문 발송 없음, 남은 글 보류 |
| 서버 OS 시간대가 UTC | KST 기준 동일한 배치·보류·발송 결과 |
| 정상·실패 수집 종료 | 브라우저 종료, 잠금 해제 |

판정·저장·전송 실패 테스트는 네트워크 없이 고정 데이터와 가짜 Discord 전송 함수로 재현한다. 실제 X 접속은 외부 상태에 의존하므로 별도 smoke check로 구분한다. 구현 완료 시 관련 Jest 검사, `npm run type-check`, `npm run build`를 실행한다.

구현 검증 기록: 결정적 Jest 검사와 Chromium DOM 검사(`npm run check:x-profile`)를 추가했다. 실제 브라우저 페이지에서 구현한 추출 함수로 상위 5개 글의 ID·원문·접힘 여부를 확인했다. 별도 설치한 headless Chromium의 비로그인 실사이트 수집은 403으로 실패했고 이를 접근 제한으로 분류했다. 서버 headless 수집, 로그인 세션 재사용, 실제 Discord 전송은 미검증이다. `X_MONITOR_ENABLED` 기본값은 비활성이며 서버 수집 검증 후 활성화한다.

## 9. 후속 확장 조건

- 기존 글 수정 알림이 필요하면 최근 일정 범위의 완전한 본문만 정규화·해시 비교한다. 접힌 본문과 펼친 본문 차이를 수정으로 오인하지 않는 검증이 먼저다. X의 수정으로 ID가 바뀌는 경우의 연결 규칙도 별도 확인한다.
- 한국어 요약이 필요하면 이미 있는 AI 서비스에 연결하되, 신규 판정과 전송 이력은 AI 결과와 분리한다.
- 여러 수신처가 필요해지면 수신처별 전송 이력으로 변경한다. 현재 전역 이력으로 여러 채널에 공유하지 않는다.
- 재게시·답글까지 필요하면 해당 탭의 접근성과 중복 규칙을 검증한 뒤 수집 범위를 확장한다.
